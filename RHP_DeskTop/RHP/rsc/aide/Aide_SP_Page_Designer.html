1. Présentation générale

1.1 À quoi sert le Designer ?

Le Designer de pages portail (écran SP_Page_Designer de RHP_DeskTop) permet de créer des pages métier complètes du portail web sans écrire une seule ligne de code portail : écrans de saisie de documents (demandes, notes de frais, déclarations…), avec entête, une ou plusieurs grilles de détail, champs calculés, contrôles de saisie, validations, workflow de signature, pièces jointes (GED) et habilitations par profil.

Tout ce que vous configurez dans le Designer est stocké dans des tables de métadonnées SQL Server (Controle_Designer, Controle_Designer_Table, Controle_Designer_Colonne, Controle_Designer_Champ, Controle_Designer_Validation, Controle_Designer_Source, Controle_Designer_Droit) puis interprété à l'exécution par le moteur générique du portail. L'enregistrement d'une page crée ou fait évoluer automatiquement les tables métier de la base (préfixe SP_) dans la même transaction.

Ce que vous pouvez construire Demandes avec circuit de validation, notes de frais avec lignes et totaux calculés, formulaires déclaratifs, consultations de données RH en lecture seule (grilles virtuelles), documents avec pièces jointes et édition imprimable — le tout publié dans le menu du portail en un clic.

1.2 Comment ça fonctionne (architecture)

◈ Chaîne de conception → exécution
① RHP_DeskTop — Designer (SP_Page_Designer) : vous décrivez la page (tables, colonnes, champs, validations, droits)  ⟶  ② Tables de métadonnées Controle_Designer* + tables métier SP_<TypeDoc>_Ent / _Det_… créées par le DDL automatique  ⟶  ③ Bouton « Publier » : la page devient visible sur le portail (statut PUBLIE)  ⟶  ④ RHP_Portail : la page apparaît dans le menu latéral ; le moteur DynamicPage / DynamicPage_Liste génère l'écran web à la volée ; le serveur ré-applique calculs et validations (le client n'est jamais cru).

Fig. 1 — De la configuration au rendu : aucun développement web n'est nécessaire.

Sécurité d'architecture Le portail ne reçoit jamais de nom de table ni de colonne du navigateur : seulement le code page et des données. Tout est résolu côté serveur depuis les métadonnées publiées ; les requêtes des sources métier restent sur le serveur ; formules et validations sont déclaratives (json), jamais du code libre — aucune injection possible.

2. Prise en main rapide : votre première page en 10 étapes

Ce tutoriel crée de bout en bout une page « Frais kilométriques » : un document avec un entête (matricule, date, commentaire), une grille de trajets (km × taux = montant calculé), un total automatique, des validations et une publication sur le portail. C'est l'exemple de référence FRAIS_KM livré avec le produit. Chaque étape renvoie au chapitre détaillé correspondant.

1

Ouvrir le Designer et créer une nouvelle page

Menu RHP_DeskTop : Système ▸ Utilitaires avancés ▸ Designer de pages portail. Cliquez Nouveau ➕. Le code page est généré automatiquement (ex. PG_20260814_000001) : il est immuable. Saisissez le nom de la page : Frais kilométriques (c'est le titre qui apparaîtra dans le menu du portail).

2

Définir le type document

Onglet « Conception de la page », champ Type document : saisissez FKM (2 à 10 caractères alphanumériques, commence par une lettre, en majuscules). Ce code est unique dans toute l'application et immuable après le premier enregistrement : il pilote les noms physiques des tables (SP_FKM_Ent, SP_FKM_Det_LIGNES) et sert de code au workflow de signature. → détails §7.

3

Déclarer les tables

Onglet « Structure des tables » ▸ sous-onglet Tables : la table d'entête ENT existe déjà (elle est créée automatiquement, insuppressible). Ajoutez une ligne : Table = LIGNES, Libellé = Trajets parcourus ; cochez Ajout, Modif., Suppr., Dupliq. ; Règle suppression = CASCADE. Le nom physique SP_FKM_Det_LIGNES se calcule tout seul. → détails §4.1.

4

Déclarer les colonnes physiques

Sous-onglet Colonnes physiques, ajoutez :

5

Poser les champs de l'entête

Onglet « Champs de la page ». Astuce : tapez dans la colonne Champ le nom exact d'une colonne physique (ex. Matricule) → le Designer propose automatiquement colonne, libellé, type de contrôle déduit du type SQL, rang, obligatoire… Complétez :

  • Matricule : type ZOOM, double-clic sur N° Zoom → choisir le zoom des agents MS067, Valeur par défaut = GV_MATRICULE (pré-rempli avec l'agent connecté), Obligatoire ✔ ;
  • Dat_Demande : type DATE, valeur par défaut GV_NOW ;
  • Commentaire : type MEMO, largeur 6 ;
  • Total : type CALCULE (l'état passe automatiquement à « Affiché »), Persisté ✔, Format = MNT, Décimales = 2 ; double-clic sur Formule (json) → assistant : choisir la famille Tableau (somme…) ▸ SOMME, colonne Mnt → la formule SOMME(Mnt) est générée. → détails §6 et §10.
6

Poser les champs de la grille de trajets

Toujours dans « Champs de la page », table LIGNES :

  • L_Trajet → colonne Trajet, type TEXT ;
  • L_Km → colonne Km, type DEC, décimales 2 ;
  • L_Tx → colonne Tx, type DEC, décimales 2 ;
  • L_Mnt → colonne Mnt, type CALCULE, Persisté ✔ ; formule (double-clic « Formule ») : tapez ARRONDI(Km * Tx; 2) en vous aidant des listes et boutons. Le montant de chaque ligne se calcule en direct à la saisie.
  • Pied de grille : champ Pied_Mnt, table LIGNES, colonne laissée vide, type CALCULE, formule SOMME(Mnt), format MNT → affiché sous la grille (« Total des trajets : 152,30 »).
7

Ajouter les validations

Onglet « Comportement », clic droit ▸ « Créer / modifier une règle avec l'assistant… » :

  • V01 — « Un champ doit être renseigné » sur Matricule, niveau Bloquant ;
  • V02 — « Nombre de lignes d'un tableau » sur LIGNES, au moins 1, bloquant (message : « Au moins une ligne de trajet est requise. ») ;
  • V03 — « Valeur entre deux bornes » sur L_Km, entre 0 et 1000, niveau Avertissement (l'utilisateur pourra continuer après confirmation).

→ détails §8 et §11.

8

Renseigner la conception (menu, actions, workflow, GED)

Onglet « Conception de la page » : Section portail = MesDemandes (créez vos propres sections avec le bouton +), Rang = 90, Icône = Commute (liste illustrée). Cochez Workflow de signature actif (les règles de signataires se règlent ensuite via le bouton « Règles du workflow de signature »), GED active pour les pièces jointes, et les actions Enregistrer / Soumettre en signature. → détails §7.

9

Attribuer les habilitations

Onglet « Habilitations » : une ligne par profil. Pour une page ouverte à tous, laissez « Accès personnalisé » décoché (consultation libre) et cochez pour chaque profil les actions autorisées (Créer, Modifier, Supprimer, Valider, Imprimer, GED). Astuce : clic droit sur l'entête d'une colonne → « Cocher … pour tous les profils ». → détails §9.

10

Enregistrer, vérifier le DDL, publier

① Enregistrer 💾 (ou touche Entrée) : les contrôles de cohérence s'exécutent, puis les tables SP_FKM_Ent et SP_FKM_Det_LIGNES sont créées dans la même transaction. ② Aperçu DDL 📜 : visualisez le script SQL qui a été / serait exécuté. ③ Publier ✅ : après les contrôles de publication, le message confirme : « Page publiée avec succès. Elle apparaît dans le portail à la section 'Demandes et documents' (rang 90). » Sur le portail, ouvrez Demandes et documents ▸ Frais kilométriques : la liste s'affiche, bouton Nouveau → votre document est prêt. → détails §14 et §15.

Félicitations Vous maîtrisez déjà 80 % du Designer. Les chapitres suivants détaillent chaque onglet, chaque assistant (formules, validations, sources, mapping) et des exemples avancés (grille virtuelle alimentée par une requête SQL, validations par source métier, champs SOURCE…).

3. Visite guidée de l'écran

3.1 Accès et droits nécessaires

  • Chemin : RHP_DeskTop ▸ Système ▸ Utilitaires avancés ▸ Designer de pages portail.
  • Par défaut, seul le profil super-admin (code 1) a tous les droits sur l'écran ; étendez l'accès via l'écran standard Admin_Profile. Les boutons Enregistrer, Supprimer, Dupliquer et Publier sont de plus protégés par la fonction de sécurité SC.
  • Prérequis technique : les scripts du module (001_SP_Designer_Metadata.sql et suivants, dossier RHP_Portail\rhpBE\sql\SP_Designer) doivent avoir été appliqués à la base. Sinon l'écran affiche un message bloquant indiquant la migration à jouer (ex. « Appliquez la migration 006_SP_Designer_Evolutions.sql (grilles virtuelles) »).

3.3 Règles d'or de l'écran

  • Rien n'est en base tant que vous n'avez pas cliqué « Enregistrer » : les grilles sont des zones de travail mémoire.
  • Les colonnes de grille grisées sont en lecture seule ; celles marquées d'un comportement au double-clic (« Requête SQL », « Paramètres », « Formule (json) », « Rubrique », « N° Zoom », « Mapping paramètres ») affichent un curseur main au survol et ouvrent un assistant — le json technique est toujours généré, jamais saisi à la main.
  • La touche Suppr supprime la ligne sélectionnée d'une grille (avec contrôles : impossible de supprimer la table ENT, une table encore référencée, ou une colonne utilisée par des champs).
  • La touche F1 (ou le bouton Aide de la barre d'outils) ouvre cette aide à tout moment, dans le navigateur par défaut.
  • Les listes déroulantes des grilles sont fermées (valeurs prédéterminées partagées avec les contrôles d'enregistrement) : impossible de saisir une valeur hors domaine.
  • Les booléens sont des cases à cocher ; les entêtes de colonnes sont des libellés utilisateur (« Type source », jamais Typ_Source).

1

Que voulez-vous vérifier ?

Choix du type de règle dans une liste en langage clair : « Un champ doit être renseigné (obligatoire) », « Comparer deux champs entre eux (ex : date de fin ≥ date de début) », « Comparer un champ à une valeur fixe », « La valeur doit faire partie d'une liste autorisée », « Valeur minimale / maximale », « Valeur entre deux bornes », « Longueur minimale / maximale du texte », « Format du texte (modèle prédéfini ou personnalisé) », « Interdire les doublons dans un tableau », « Nombre de lignes d'un tableau (min/max) », « Règle personnalisée (combinaison de conditions) ». Une aide contextuelle s'affiche pour chaque type.

2

Champ / tableau concerné

Liste des champs de la page (ou du tableau pour « Nombre de lignes »). Cette étape fixe automatiquement la portée : CHAMP (entête), LIGNE (champ d'un détail), DETAIL (doublons / nombre de lignes), DOCUMENT (règle personnalisée).

3

Paramètres de la règle

Un panneau adapté au type : valeur unique ; bornes « Entre … et … (bornes incluses) » ; liste de valeurs séparées par des points-virgules (CDI ; CDD ; INTERIM) ; modèle de format prédéfini (E-mail, Téléphone FR, Code postal, Chiffres uniquement, Lettres uniquement, Personnalisé) ; opérateur de comparaison + autre champ ou constante ; colonnes de la combinaison anti-doublon ; bornes « au moins / au plus » pour un tableau.

4

Quand la règle doit-elle s'appliquer ? (facultatif)

12. Sources métier — guide complet

Une source métier est une requête SQL (ou un appel de procédure autorisée) paramétrée, sécurisée et réutilisable, déclarée une fois dans le catalogue (onglet « Sources externes ») et consommable par n'importe quelle page. Trois usages : champ SOURCE (valeur affichée), grille virtuelle (tableau calculé), validation SOURCE (contrôle serveur).

12.1 Créer une source pas à pas

1

Ajouter une ligne dans le catalogue

Onglet « Sources externes » → nouvelle ligne : Code source (ex. sp_solde_conge_date), Libellé métier, Type = SQL, Retour = SCALAIRE ou TABLE, Profil requis éventuel, Active ✔.

2

Écrire la requête (double-clic sur « Requête SQL »)

L'éditeur (Zoom_SP_SqlSource) contrôle la requête en temps réel (bandeau vert « Requête conforme au contrôle d'injection. » ou rouge avec le motif du refus). Règles — miroir exact du garde-fou serveur :

  • Lecture seule uniquement : la requête doit commencer par SELECT, WITH ou EXEC dbo.Sys_* ; une seule instruction ;
  • mots-clés interdits : insert, update, delete, merge, drop, alter, create, truncate, grant, revoke, backup, restore, shutdown, kill, waitfor, openrowset, opendatasource, xp_* ;
  • procédures système sp_* (minuscules) interdites — les tables métier SP_ (majuscules) restent lisibles ;
  • paramètres écrits @xxx dans le texte ; @id_Societe est toujours injecté par le serveur : ne l'utilisez qu'en lecture, sans jamais le déclarer.
3

Déclarer les paramètres (double-clic sur « Paramètres »)

L'assistant (Zoom_SP_Assistant_ParamSource) détecte les @xxx de la requête et les propose dans la liste des noms. Pour chacun : Nom (sans le @), Type (Texte nvarchar, Nombre entier int, Nombre décimal, Date, Date et heure, Oui/Non bit), Obligatoire. Il contrôle la cohérence dans les deux sens : paramètre déclaré mais absent de la requête → erreur ; @xxx utilisé mais non déclaré → erreur (sauf auto-injectés).

4

Enregistrer la page

Le catalogue est enregistré avec la page (ajouts/mises à jour par code source ; une source n'est jamais supprimée automatiquement). La source devient immédiatement disponible dans les listes « Source métier » des onglets Tables et Champs.

12.3 Exemples réels de sources (extraits du référentiel produit)

Exemple A — scalaire simple : solde de congé à une date

-- Code : sp_solde_conge_date · Type : SQL · Retour : SCALAIRE
-- Paramètres : [{"Nom":"Matricule","Typ":"nvarchar","Obligatoire":true},
--               {"Nom":"DatRef","Typ":"nvarchar","Obligatoire":true}]
select isnull(min(c.Solde_Conge), 0) as Solde_Conge
from (select convert(date, dateadd(hour, 12, convert(datetimeoffset, @DatRef))) as DatRef) d
cross apply dbo.Sys_Rh_Conge(@id_Societe, d.DatRef) c
where c.Matricule = @Matricule
Convention dates Les paramètres date arrivent du portail en chaîne ISO ; la canonisation dateadd(hour, 12, convert(datetimeoffset, @…)) rétablit la lecture d'horloge locale quel que soit le fuseau — reprenez ce motif dans vos propres sources datées.

Exemple B — scalaire avec règle de gestion : avances en cours d'un agent

-- Code : sp_avances_encours · Retour : SCALAIRE · Paramètres : Matricule (obligatoire)
select isnull(sum(isnull(Montant_Avance, 0) - isnull(Reglement, 0)), 0) as mnt
from dbo.RH_Paie_Avance
where id_Societe = @id_Societe and Matricule = @Matricule

Exemple C — retour TABLE : découpe d'un congé par période de paie

-- Code : sp_cng_detail · Retour : TABLE · Paramètres : Matricule, Deb, Fin (obligatoires), DebPm, FinPm (facultatifs)
-- Alimente une GRILLE VIRTUELLE : colonnes restituées Dat_Deb, Dat_Fin, Duree_Globale, Repos_Hebdomadaire, Jours_Feries, Duree_Conge
with d as (
  select convert(date, dateadd(hour, 12, convert(datetimeoffset, @Deb))) as Deb,
         convert(date, dateadd(hour, 12, convert(datetimeoffset, @Fin))) as Fin
), …
select PDeb as Dat_Deb, PFin as Dat_Fin, Duree_Globale,
       sum(EstRepos) as Repos_Hebdomadaire,
       sum(case when EstRepos = 1 then 0 else EstFerie end) as Jours_Feries,
       case when Duree_Globale - sum(EstRepos) - … < 0 then 0 else … end as Duree_Conge
from j2
group by PDeb, PFin, Duree_Globale
order by PDeb
option (maxrecursion 0)

Les noms de colonnes du SELECT final deviennent les colonnes à déclarer dans « Colonnes physiques » de la grille virtuelle (§13). La requête complète (CTE récursive sur les jours, jours ouvrables de la société, jours fériés) est livrée dans 006_Duplicatas_Pages_Standards\001_deploy.sql.

Exemple D — appel de procédure autorisée (type PROC)

-- Type : PROC · seuls les appels EXEC dbo.Sys_* sont admis
EXEC dbo.Sys_MaProcedureMetier @id_Societe, @Matricule, @Deb, @Fin

12.4 Usage 1 — le champ SOURCE

Un champ de type SOURCE affiche une valeur calculée par la base (solde, encours, durée réglementaire…) et la ré-évalue dès qu'un paramètre change :

  • Type contrôle = SOURCE ; Source métier = le code de la source ; état A (affiché) ;
  • Formule (json) = le mapping des paramètres (même format que les grilles virtuelles) : 
    {"source":"sp_cng_duree","mapping":{
  "Deb":  {"ref":"Dat_Deb_Conge"},
  "Fin":  {"ref":"Dat_Fin_Conge"},
  "DebPm":{"ref":"Dat_Deb_am_pm"},
  "FinPm":{"ref":"Dat_Fin_am_pm"},
  "Typ":  {"ref":"Typ_Conge"}}}
    Chaque paramètre est alimenté par {"ref":"ChampEntete"} (un champ de l'entête) ou {"const":"valeur"}.
  • Persisté ✔ + colonne physique affectée : la valeur est stockée (le serveur ré-exécute la source à l'enregistrement — la valeur du navigateur n'est jamais crue). Colonne vide : valeur d'affichage seule, recalculée à chaque ouverture.

Exemple réel (page congés) : les champs Repos_Hebdomadaire, Jours_Feries, Duree_Conge et Solde_Conge sont quatre champs SOURCE persistés/affichés, alimentés par les sources sp_cng_repos, sp_cng_feries, sp_cng_duree, sp_solde_conge_date, avec Format NUM et décimales 0 ou 1.

12.5 Usage 2 — la grille virtuelle

Une table de détail dont la colonne « Source métier » est renseignée (source de retour TABLE) devient une grille recalculée par la source à chaque changement d'un champ mappé, en lecture seule, jamais stockée. Guide complet au chapitre 13.

12.6 Usage 3 — la validation SOURCE (contrôle serveur)

Une règle de type SOURCE exécute une source au moment de l'enregistrement, côté serveur, injecte son résultat scalaire sous le nom @result dans une condition, et bloque si la condition échoue. Non prise en charge par l'assistant : saisissez le json directement dans la colonne « Paramètres (json) » de la grille des validations :

{"source":"sp_cng_chevauchement",
 "mapping":{"Matricule":{"ref":"Matricule"},
            "Deb":{"ref":"Dat_Deb_Conge"},
            "Fin":{"ref":"Dat_Fin_Conge"},
            "Num_Doc":{"ref":"Num_Doc"}},   -- le document courant est exclu du contrôle
 "cond":{"op":"EQ","args":[{"ref":"@result"},{"const":0}]}}

Message associé : « Il existe au moins un congé en chevauchement avec cette demande. » — portée DOCUMENT, niveau B. Autres exemples réels : sp_cng_periode_cloturee (période de paie clôturée), sp_cng_controle_paie (début postérieur à la dernière paie), sp_check_proprietaire (le document appartient à l'agent connecté).

Colonnes techniques disponibles Les validations et calculs voient aussi les colonnes techniques Num_Doc, Statut, Created_By — pratique pour exclure le document courant d'un contrôle d'unicité/chevauchement.

12.7 Sécurité et gouvernance

  • Le texte SQL ne quitte jamais le serveur : le portail n'envoie que le code source et les valeurs des paramètres.
  • Chaque nom de paramètre est validé (identifiant SQL sain) ; les valeurs sont passées en paramètres typés — aucune injection.
  • Profil requis : restreint l'exécution à un profil (le super-admin 1 passe toujours).
  • Active décochée : la source devient inexécutable ; la publication d'une page qui l'utilise est refusée (« source inexistante ou inactive »).
  • Une source défaillante à l'enregistrement (timeout, erreur SQL) bloque l'enregistrement si elle alimente une validation de niveau B.

13. Grilles virtuelles — guide complet

Une grille virtuelle est un tableau de détail sans table physique : ses lignes sont calculées en direct par une source métier de retour TABLE, à partir des valeurs de l'entête. Cas d'usage : découpe d'un congé par période de paie, échéancier calculé, simulation, consultation d'un référentiel…

13.1 Mise en place pas à pas (exemple réel : « Détail par période de paie »)

1

Créer la source de retour TABLE

Catalogue des sources : sp_cng_detail, retour TABLE, paramètres Matricule, Deb, Fin (obligatoires), DebPm, FinPm (facultatifs). Le SELECT final retourne les colonnes Dat_Deb, Dat_Fin, Duree_Globale, Repos_Hebdomadaire, Jours_Feries, Duree_Conge (§12.3 exemple C).

2

Déclarer la table de détail et lui affecter la source

Onglet « Structure des tables » : nouvelle table PERIODES, libellé « Détail par période de paie » ; colonne Source métier = sp_cng_detail. Le Designer affiche : « La table 'PERIODES' est maintenant une GRILLE VIRTUELLE alimentée par la source 'sp_cng_detail' : - aucune table physique ne sera créée (la grille est recalculée par la source) ; - la grille est en lecture seule (Ajout/Modif./Suppr. décochés) ; - déclarez dans 'Colonnes physiques' les colonnes RESTITUÉES par la source ; - double-cliquez sur 'Mapping paramètres' pour alimenter les paramètres de la source. » Le nom physique devient SP_<TypeDoc>_Virt_PERIODES (jamais créé en base).

3

Déclarer les colonnes restituées

Sous-onglet « Colonnes physiques », table PERIODES : déclarez chaque colonne du SELECT de la source avec son libellé et un type SQL cohérent (Dat_Deb date « Du », Dat_Fin date « Au », Duree_Globale float « Durée globale », Repos_Hebdomadaire float « Repos », Jours_Feries float « Jours fériés », Duree_Conge float « Congé »). Ces déclarations ne créent rien en base : elles décrivent la sortie pour le rendu et les validations.

4

Alimenter les paramètres (assistant Mapping)

Double-clic sur la cellule « Mapping paramètres » de la table : pour chaque paramètre déclaré de la source, choisissez « Champ de l'entête » (liste des colonnes ENT + techniques, hors RV) ou « Constante ». L'assistant pré-remplit par homonymie (un champ nommé comme le paramètre est proposé) et exige que tout paramètre obligatoire soit alimenté. Json généré automatiquement :

Onglet « Champs de la page », table PERIODES : un champ par colonne (P_Dat_Deb → DATE état R, P_Duree_Globale → DEC état R, etc.), « Visible grille » ✔, rangs et largeurs de colonnes. État conseillé : R (lecture seule) partout.

13.3 Règles et contrôles automatiques

  • L'entête ENT ne peut pas être virtuelle (« l'entête ENT est toujours une table physique »).
  • La source doit exister, être active et de retour TABLE — sinon enregistrement/publication refusés (« une grille virtuelle exige une source de retour TABLE »).
  • Une table devenue virtuelle alors qu'elle existait physiquement est refusée.
  • Mapping : chaque paramètre alimenté doit être déclaré dans la source ; chaque ref doit exister parmi les colonnes de l'entête (déclarées + techniques hors RV) ; tout paramètre obligatoire doit être alimenté — messages d'erreur précis à l'enregistrement.
  • Les cases Ajout/Modif./Suppr./Dupliq. sont forcées à décoché (lecture seule).
  • Les lignes virtuelles ne sont jamais postées par le navigateur ni écrites : le serveur ré-exécute la source — les validations de portée DETAIL (ex. NB_LIGNES) s'appliquent sur ces lignes.

Le bouton Enregistrer (ou Entrée) exécute d'abord une batterie de contrôles, dans l'ordre — chaque échec affiche un message précis et rien n'est écrit :

Bandeau« Code page invalide (lettres/chiffres/_, 3 à 30 caractères, ne commence pas par 'Page'). » · « Type document invalide (2 à 10 caractères alphanumériques, commence par une lettre). » · « Le type document 'X' est déjà utilisé par la page 'Y' : choisissez un autre code. » · nom de page et section portail obligatoires.
TablesIdentifiants SQL valides et hors mots réservés ; codes uniques ; exactement une ENT ; noms physiques préfixés SP_, uniques dans la page et dans la base ; pas de table « orpheline » ; grille virtuelle cohérente (§13.3).

ValidationsPortée et type valides ; code unique ; table configurée ; message obligatoire.
HabilitationsPas de profil en doublon.

Puis tout est écrit dans une seule transaction : métadonnées (mise à jour de Controle_Designer, purge et réinsertion des lignes filles, mise à jour du catalogue de sources) puis création/migration des tables métier (CREATE TABLE / ALTER TABLE … ADD, index IX_/UX_, clé étrangère détail→entête ON DELETE CASCADE si demandé). Toute erreur SQL annule tout (rollback). Le journal Controle_Designer_DDL_Log conserve chaque exécution (script, résultat, login, date). Message de succès : « Enregistré avec succès. » suivi du récapitulatif DDL (tables créées, colonnes ajoutées, avertissements).

Migration non destructive Une colonne retirée de la configuration n'est jamais supprimée en base (avertissement « ATTENTION … Elle n'est PAS supprimée ») ; une table retirée de la configuration devient une table orpheline, conservée elle aussi — elle ne sera supprimée, si elle est vide, qu'à la suppression de la page (→ §14.6). Le DDL étant non destructif, ré-enregistrer une page publiée ne l'invalide pas : elle reste publiée.

14.3 Publier / Désactiver

Le bouton Publier exige une page enregistrée, puis vérifie (relecture en base) : tables physiques existantes, colonnes existantes, grilles virtuelles cohérentes, zooms et rubriques des champs existants, sources existantes et actives, absence de référence circulaire entre champs calculés, habilitations cohérentes (accès personnalisé ⇒ au moins un « Consulter »), section de menu renseignée, workflow actif ⇒ type document renseigné. En cas d'échec : « Publication impossible : - … » liste chaque problème.

La publication : passe le statut à PUBLIE, horodate Dat_Publication, incrémente Version_Page, enregistre l'écran portail SPP_<CodPage> (liaison GED), et déclare le type document au moteur de workflow si actif. Message final : « Page publiée avec succès. Elle apparaît dans le portail à la section 'Demandes et documents' (rang 90). »

Sur une page déjà publiée, le même bouton propose la désactivation : la page disparaît du portail, les documents sont conservés (statut DESACTIVE).

14.4 Dupliquer une page

Dupliquer (page enregistrée requise) copie tout le paramétrage affiché — tables, colonnes, champs, validations, habilitations — sous une nouvelle identité : nouveau code page généré, nom préfixé « Copie de », statut Brouillon, et type document vidé, à ressaisir (unique : il pilotera les nouvelles tables SP_<NouveauType>_…). Rien n'est écrit en base avant « Enregistrer » ; la page d'origine n'est jamais modifiée.

Non repris par la copie Le catalogue des sources (global, partagé) · les règles du workflow de signature (propres au type document — le message de confirmation vous y invite : « redéfinissez-les pour le nouveau type document ») · les artefacts de publication (écran SPP_, version, dates).

14.5 Exporter / Importer la configuration (JSON)

Les boutons Exporter JSON et Importer JSON permettent de transférer une page configurée d'un environnement RHP vers un autre (ou d'en conserver une copie de sauvegarde), sans jamais manipuler les tables SQL à la main. Le fichier produit est un json lisible, versionné (format: "RHP_PAGE_DESIGNER", version: "1.0"), nommé RHP_Page_<CodePage>_<AAAAMMJJ_HHMMSS>.json.

Contenu du fichier : identification de la page (code, type document, nom, section de menu, rang, icône, options workflow / GED / actions) · structure SQL logique (tables ENT/DET, colonnes physiques avec types, tailles, nullabilité, défauts, index) · champs de la page (entête et colonnes de grilles, avec formules, zooms, rubriques, sources) · grilles virtuelles (source + mapping) · validations déclaratives · sources métier utilisées par la page. Les habilitations ne figurent JAMAIS dans le fichier (ni profils, ni droits, ni l'option « Accès personnalisé » en mise à jour).

Exporter

Ouvrez la page, cliquez Exporter JSON, choisissez l'emplacement : l'état affiché (saisies validées incluses, miroir de « Dupliquer ») est sérialisé. Le message de confirmation rappelle les compteurs exportés.

Importer — dans le Designer, jamais directement en base

Importer JSON enchaîne : lecture du fichier → validation complète (format, version, structure, domaines, doublons, références entre éléments, sources, mappings) → prévisualisation (création ou mise à jour, éléments détectés, ajouts / modifications / suppressions / inchangés, dépendances non résolues) → au « Valider » seulement, la configuration est chargée dans les contrôles et grilles du Designer. Aucune écriture en base n'a lieu à ce stade : c'est le bouton Enregistrer qui applique tous les contrôles standards et génère/migre les tables SQL. Un fichier invalide est rejeté avec la liste précise des anomalies, sans rien modifier à l'écran.

  • Création : le code page du fichier est inconnu (ou absent ⇒ code automatique) — l'écran passe en mode création, toutes les grilles sont alimentées ; le statut repart à BROUILLON.
  • Mise à jour : le code page existe — la configuration du fichier remplace celle de l'écran (synchronisation : ajouts, modifications, suppressions d'éléments). Le type document doit être identique (il est immuable après création : un écart bloque l'import). Les habilitations existantes sont intégralement préservées.
  • Sources métier : le catalogue étant global, les sources du fichier sont fusionnées par code (créées ou mises à jour), jamais supprimées.
  • Dépendances (section de menu, zooms, rubriques, modèle d'édition, profils de sources) : résolues par code fonctionnel dans la base cible ; une dépendance introuvable produit un avertissement explicite à corriger dans l'écran avant l'enregistrement — la sauvegarde reste bloquée tant qu'une donnée obligatoire manque.
Traçabilité Le fichier embarque date d'export, utilisateur et version RHP. L'import d'une page existante est journalisé dans Controle_Designer_DDL_Log (opération IMPORT : utilisateur, date, nombre d'éléments ajoutés / modifiés / supprimés). La migration SQL reste non destructive : une colonne ou table retirée par l'import disparaît de la configuration mais n'est jamais supprimée physiquement (signalée à l'enregistrement ; une table orpheline vide ne sera supprimée qu'à la suppression de la page — → §14.6).

14.6 Supprimer une page

Conditions — toutes obligatoires : page enregistrée, tables SQL vides — chaque table physique de la page (entête et détails, y compris les tables orphelines du préfixe SP_<TypeDocument>_%, ex. détail retiré de la configuration après génération ; les détails virtuels alimentés par une source n'ont pas de table physique) ne doit contenir aucune ligne — et aucune référence extérieure : aucune clé étrangère d'une table extérieure ne doit pointer vers ces tables (le message liste les tables non vides ou les références le cas échéant). Le statut n'est pas un critère : brouillon, publiée ou désactivée, une page sans donnée se supprime. La suppression purge les métadonnées de la page (dans l'ordre des clés étrangères, y compris le journal DDL), supprime physiquement les tables SQL vides (détails et orphelines d'abord, entête en dernier — les clés étrangères internes détail → entête partent avec elles) ainsi que les éventuelles configurations d'audit (espions) posées sur ces tables, les artefacts de publication (écran portail SPP_<CodPage> et déclaration du type document au moteur de workflow — uniquement si elle est rattachée à cet écran) et les règles de workflow orphelines du type document (signalés dans la confirmation). Aucune donnée n'est jamais détruite : seules des tables vides sont supprimées ; le catalogue des sources n'est pas touché.

14.7 Vie des documents (rappels utiles au concepteur)

  • Numérotation : <TypeDocument><idSociete>-<année><séquence 6 chiffres> (ex. FKM1-2026000001), attribuée à l'enregistrement.
  • Concurrence optimiste : la colonne RV détecte les conflits — « Document modifié par un autre utilisateur. Rechargez la page. » ; un verrou d'accès signale aussi « Document utilisé par : X ».
  • Statuts figeants : au-delà de certains statuts de signature (défaut SG,RJ,SP,VA — Signé, Rejeté, Suspendu, Validé), le document n'est plus modifiable ni supprimable.
  • Audit systématique : Dat_Crea / Created_By / Dat_Modif / Modified_By.
  • Garde paie : l'enregistrement est refusé si une préparation de paie est en cours.

17. Bonnes pratiques et dépannage

17.1 Check-list avant de publier

  • ☐ Le type document est définitif (immuable après enregistrement) et parlant : FKM, CGE, ATD…
  • ☐ Chaque table a au moins une colonne ; chaque colonne utile est reliée à un seul champ.
  • ☐ Les champs ZOOM ont un N° Zoom, les RUBRIQUE une rubrique, les CALCULE une formule valide et un format.
  • ☐ Les validations ont toutes un message clair et le bon niveau (B/W/I).
  • ☐ Les sources utilisées sont actives ; les paramètres obligatoires des grilles virtuelles sont tous alimentés.
  • ☐ Pas de référence circulaire entre champs calculés (le bouton Publier le signale).
  • ☐ Habilitations : au moins un profil « Consulter » si accès personnalisé ; sinon accès décoché.
  • ☐ Section, rang et icône renseignés ; Aperçu DDL relu ; test complet sur un document réel après publication.

17.3 Bonnes pratiques de conception

  • Nommez clairement : codes de tables courts et stables (LIGNES, PERIODES), colonnes en PascalCase métier (Dat_Deb_Conge), libellés utilisateurs soignés.
  • Préférez les assistants à toute saisie manuelle de json ; n'éditez le json qu'en « mode avancé » documenté.
  • Un champ = une colonne, une colonne = un champ ; utilisez les champs sans colonne pour l'affichage et les pieds de grille.
  • Testez les formules avec le testeur intégré (étape 3) avant d'enregistrer.
  • Avertissement (W) plutôt que blocage (B) pour les contrôles de plausibilité (kilométrage inhabituel…) ; blocage pour l'intégrité.
  • Centralisez le SQL métier dans les sources (catalogue réutilisable, contrôle d'injection, restriction par profil) plutôt que de multiplier les variantes.
  • Dupliquez une page éprouvée plutôt que de repartir de zéro.
  • Aperçu DDL systématique avant publication sur une base de production ; le journal Controle_Designer_DDL_Log garde la trace de chaque exécution.
  • Documentez chaque champ délicat dans sa colonne Aide (affichée sur le portail).

18. Foire aux questions

Comment accéder à cette aide depuis l'écran ?

Par le bouton ? Aide de la barre d'outils du Designer (juste après « Enregistrer »), ou par la touche F1 à tout moment : le guide s'ouvre dans le navigateur par défaut (il est déployé avec l'application, dossier rsc\aide).

Le code page peut-il être changé ?

Non. Il est généré (PG_<date>_<séquence>) et immuable. Seuls le nom, la structure et les paramètres évoluent.

Le type document peut-il être changé après enregistrement ?

Non plus : il pilote les noms physiques des tables et le code workflow. Pour « renommer », dupliquez la page sous un nouveau type document.

Que risque-t-on en ré-enregistrant une page déjà publiée ?

Rien : le DDL est non destructif (ALTER ADD uniquement), la publication est conservée, et le portail voit les changements sous ~60 secondes.

Comment supprimer une colonne devenue inutile ?

Retirez d'abord les champs qui l'utilisent, puis la colonne, et enregistrez : la colonne reste physiquement en base (migration non destructive, avertissement dans l'aperçu DDL) mais n'est plus utilisée ni affichée.

Quelle différence entre états R et A ?

R (lecture seule) : valeur stockée, affichée grisée, saisie impossible. A (affiché) : valeur non saisissable, typiquement calculée ou issue d'une source. I : non rendu.

« Obligatoire » (case) ou validation REQUIRED ?

La case ajoute * au libellé (indication visuelle) ; la règle REQUIRED (niveau B) réalise le blocage effectif à l'enregistrement. Utilisez les deux ensemble.

Qui peut exécuter une source métier ?

Tout profil si « Profil requis » est vide ; sinon uniquement ce profil (et le super-admin). Le SQL n'est jamais visible côté navigateur.

Comment déboguer une formule ?

Étape 3 de l'assistant : saisissez des valeurs de test (dates jj/mm/aaaa ; colonnes de tableau séparées par des points-virgules, ex. 10 ; 20,5 ; 3) et cliquez « Calculer ».

Pourquoi ma grille virtuelle est-elle vide ?

Vérifiez : source active et de retour TABLE ; paramètres obligatoires tous mappés ; les champs d'entête mappés sont renseignés ; la requête retourne des lignes pour ces valeurs (testez-la dans SSMS avec les mêmes paramètres et le bon @id_Societe).

Comment ouvrir directement un document du portail ?

URL : /myspace/SPP_<CodPage>/<titre>/<Num_Doc> ; la liste est /myspace/SPPL_<CodPage>/<titre>.
